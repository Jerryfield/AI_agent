# AI Application Evolution

> 从 Traditional Application 到 Agentic System 的工程演进认知

---

## 1. Core Question

AI Application 是如何逐渐演进到 Agentic System 的？

这一篇笔记关注的不是“哪个概念更高级”，而是理解：

- 软件中的“智能”来自哪里；
- 系统的控制流由谁决定；
- 模型拥有多少运行时决策权；
- 为什么 LLM Application、Workflow、Agent 之间存在明确边界；
- 为什么 Agentic System 是系统架构概念，而不是简单的“更高级 Agent”。

---

## 2. Mental Model

从能力演进角度，可以先这样理解：

```text
Traditional Application
        ↓
AI Application
        ↓
LLM Application
        ↓
AI Workflow / AI Agent
        ↓
Agentic System
```

但从严格的工程分类看，更准确的结构是：

```text
                    Software Application
                           │
          ┌────────────────┴────────────────┐
          │                                 │
Traditional Application              AI Application
                                            │
                                   ┌────────┴────────┐
                                   │                 │
                             Traditional ML      LLM Application
                             CV / NLP / etc.           │
                                                       │
                                      ┌────────────────┴───────────────┐
                                      │                                │
                                  AI Workflow                       AI Agent
                                      │                                │
                              Code controls path              Model participates
                                                            in control flow
                                      │                                │
                                      └──────────────┬─────────────────┘
                                                     │
                                              Agentic System
```

因此：

- LLM Application 是 AI Application 的一种重要形态；
- Workflow 和 Agent 是两种不同的系统组织方式；
- Agentic System 可以同时包含 Workflow、Agent、Tools、State、Memory、RAG、Human-in-the-loop 等组件。

---

## 3. Traditional Application

### 3.1 核心特征

Traditional Application 中，程序行为主要由开发者提前编码。

```text
Developer
   ↓
Code / Rules
   ↓
Application
   ↓
Result
```

例如：

```python
def refund(order):
    if order.status != "shipped":
        refund_payment(order)
    else:
        create_return_request(order)
```

程序在运行时主要执行开发者预先定义好的：

- 条件判断；
- 业务规则；
- 算法；
- 状态机；
- 数据库操作；
- API 调用。

### 3.2 我的理解

> Traditional Application 的核心是：**Developer encodes behavior**。

系统并不会自己学习规则，也不会在运行时自主决定一个新的执行策略。

---

## 4. AI Application

### 4.1 为什么会出现 AI Application

有些问题很难通过固定规则完整描述，例如：

- 垃圾邮件判断；
- 商品推荐；
- 图像识别；
- 风险预测；
- 异常检测；
- 语音识别。

传统方式可能需要不断增加规则：

```python
if condition_a:
    ...
elif condition_b:
    ...
elif condition_c:
    ...
```

随着输入复杂度提高，规则数量会快速膨胀。

AI Application 的变化是：

```text
Data
 ↓
Training
 ↓
Model
 ↓
Prediction
```

模型不再完全依赖开发者手写规则，而是从数据中学习某种映射关系。

### 4.2 典型结构

```text
User / Data
     ↓
Application
     ↓
AI / ML Model
     ↓
Prediction
     ↓
Application Logic
     ↓
Result
```

### 4.3 我的理解

> AI Application 的核心变化是：**Model provides learned intelligence**。

但模型通常仍然只是 Application 中的一个组件。

整个流程主要还是：

```text
Code
 ↓
Model
 ↓
Code
```

因此，AI Application 并不等于 Agent。

---

## 5. LLM Application

### 5.1 LLM 带来的变化

LLM 并不是 AI 第一次进入软件系统。

LLM 真正重要的变化在于：

> 一个通用模型开始能够通过自然语言 Instructions + Context 处理大量不同的语义任务。

例如：

- 分类；
- 信息抽取；
- 总结；
- 翻译；
- 内容生成；
- 意图识别；
- 语义判断；
- 推理。

基本结构：

```text
Instructions
+
Context
+
Input
   ↓
  LLM
   ↓
Output
```

### 5.2 工程结构

```text
User Input
    ↓
Application
    ↓
Build Context
    ↓
Instructions / Prompt
    ↓
LLM
    ↓
Structured / Text Output
    ↓
Application Logic
    ↓
Database / API
    ↓
Response
```

### 5.3 Semantic Capability

可以暂时把 LLM 理解成一种：

> Semantic Service

例如：

```python
database.query()
redis.get()
search.query()

llm.classify()
llm.extract()
llm.summarize()
llm.generate()
```

传统代码擅长：

- 数值计算；
- 权限判断；
- 状态机；
- SQL；
- 精确业务规则；
- 强确定性逻辑。

LLM 更适合：

- 自然语言理解；
- 分类；
- 信息抽取；
- 总结；
- 生成；
- 语义判断。

### 5.4 我的理解

> LLM Application = Traditional Software + LLM Semantic Capability。

同时：

> LLM 是 Application 中的一个能力组件，而不是整个 Application。

## 6. AI Workflow

### 6.1 为什么 Single LLM Call 不够

最简单的 LLM Application：

```text
User
 ↓
LLM
 ↓
Response
```

但真实业务通常需要多个步骤，例如：

```text
Search
 ↓
Generate
 ↓
Check
 ↓
Translate
 ↓
Save
```

于是出现 AI Workflow。

### 6.2 典型结构

```text
             Developer-defined Flow

User
 ↓
Search
 ↓
LLM Generate
 ↓
Validator
 ↓
Translate
 ↓
Database
 ↓
Output
```

代码可能是：

```python
sources = search(query)
article = generate(sources)

if not validate(article):
    article = regenerate(article)

translation = translate(article)
save(translation)
```

### 6.3 Workflow 的核心特征

虽然 LLM 可以参与多个节点，甚至负责分类或路由，但：

> **整体执行路径主要由开发者提前定义。**

开发者通常已经规定：

- 有哪些步骤；
- 有哪些节点；
- 节点之间如何连接；
- 什么条件进入哪个分支；
- 什么情况下重试；
- 什么情况下结束。

### 6.4 我的理解

> AI Workflow 的核心是：**Code owns the control flow**。

LLM 可以做智能判断，但系统整体流程仍然是被预先编排的。

---

## 7. AI Agent

### 7.1 从 Workflow 到 Agent 的关键变化

假设用户提出目标：

> 分析项目最近 CI 经常失败的原因，并给出修复方案。

如果开发者没有提前固定：

```text
先查 CI
↓
再查日志
↓
再看 Commit
↓
再检查依赖
```

而是提供：

```text
Goal
+
Instructions
+
Context
+
Tools
```

让模型根据当前信息动态决定下一步，就开始具有 Agent 特征。

### 7.2 典型 Agent Loop

```text
User Goal
   ↓
Model
   ↓
Decide Next Action
   ↓
Tool Call
   ↓
Tool Result / Observation
   ↓
Model
   ↓
Decide Again
   ↓
...
   ↓
Finish
```

例如：

```text
用户目标
  ↓
LLM：我需要先查看最近 CI Run
  ↓
get_ci_runs()
  ↓
Observation
  ↓
LLM：需要读取失败日志
  ↓
get_ci_log()
  ↓
Observation
  ↓
LLM：可能与最近依赖升级有关
  ↓
git_log()
  ↓
...
```

### 7.3 Agent 的核心变化

Workflow：

```text
Developer decides the execution path
```

Agent：

```text
Model decides parts of the execution path at runtime
```

因此一个非常重要的问题是：

> **Who owns the control flow?**

### 7.4 但 Agent 不是“模型控制一切”

生产环境中的 Agent 外层仍然需要 Runtime 约束：

```text
Agent Runtime
├── Tool Permissions
├── Stop Conditions
├── Max Steps
├── Token / Cost Budget
├── Timeout
├── Guardrails
├── Human Approval
└── Error Handling
```

因此更准确的描述是：

> **Model dynamically participates in control flow。**

而不是：

> Model controls everything。

---

## 8. Workflow vs Agent

这是这一篇最重要的边界。

### Workflow

```text
User
 ↓
Step A
 ↓
Step B
 ↓
Step C
 ↓
Output
```

执行路径基本可以在运行前画出来。

核心：

> Code owns the control flow.

### Agent

```text
Goal
 ↓
Model
 ↓
Action
 ↓
Observation
 ↓
Model
 ↓
Action
 ↓
...
 ↓
Finish
```

执行路径会受到运行时状态和模型决策影响。

核心：

> Model dynamically participates in control flow.

### 判断原则

不能只看：

- 是否用了 LLM；
- 是否调用了 Tool；
- 是否调用了 API；
- 是否有多个步骤。

真正应该看：

> **下一步行动是代码预先规定的，还是模型根据当前状态动态决定的？**

---

## 9. Tool Calling ≠ Agent

一个系统可能这样运行：

```text
LLM
 ↓
Search Tool
 ↓
LLM
 ↓
Database
```

但这仍然不能直接判断它是 Agent。

例如：

```python
query = llm_generate_query(user_input)
result = search(query)
answer = llm_summarize(result)
save(answer)
```

虽然这里：

- 使用了 LLM；
- 使用了 Tool；
- 有多个模型调用；

但流程依然固定：

```text
Generate Query
↓
Search
↓
Summarize
↓
Save
```

所以它更接近 AI Workflow。

因此：

> **Tool Calling 是构建 Agent 的重要基础能力，但 Tool Calling 本身不等于 Agent。**

---

## 10. Agentic System

### 10.1 Agentic System 不是“更高级的 Agent”

Agentic System 更适合从系统架构层理解。

一个真实系统可能同时包含：

```text
Workflow
+
Agent
+
Tools
+
RAG
+
Context
+
State
+
Memory
+
Human-in-the-loop
+
Evaluation
+
Tracing
+
Security
+
Runtime
```

例如 AI Software Engineering Agent：

```text
                        User
                         ↓
                  Orchestration Layer
                         │
             ┌───────────┼───────────┐
             ↓           ↓           ↓
          Workflow   Coding Agent  Review Agent
             │           │           │
            RAG        Tools       Tools
             │           │           │
           Docs      Git / Shell    Tests
                         │
                         ↓
                      Sandbox
                         │
                  Human Approval
                         │
                     Database
```

### 10.2 我的理解

> Agent 是一个能够根据目标和当前状态动态决定下一步行动的执行主体。

而：

> Agentic System 是围绕目标驱动执行构建出来的完整 AI 软件系统。

因此 Agentic System 可能包含：

- 一个 Agent；
- 多个 Agent；
- 固定 Workflow；
- Agent + Workflow 混合；
- Human-in-the-loop；
- 非 AI 的传统代码组件。

## 11. Core Evolution

可以把整个演进压缩成下面几句话。

### Traditional Application

```text
Developer encodes behavior.
```

开发者通过代码和规则定义系统行为。

### AI Application

```text
Model provides learned intelligence.
```

模型通过训练数据获得预测或识别能力。

### LLM Application

```text
LLM provides general semantic capability.
```

通用语言模型负责自然语言和语义任务。

### AI Workflow

```text
Code owns the control flow.
```

多个 LLM / Tool 被组合，但流程主要由代码预定义。

### AI Agent

```text
Model dynamically participates in control flow.
```

模型根据 Goal、Context、State 和 Observation 动态决定下一步行动。

### Agentic System

```text
Agents + Workflows + Engineering Infrastructure.
```

围绕复杂目标组合 Agent、Workflow、Tools、State、Memory、RAG、Human、Runtime、Evals、Security 等能力。

## 12. Control Flow 是最关键的观察维度

判断一个系统处于哪个层次，不应该只问：

> 它有没有使用 AI？

而应该进一步问：

### 12.1 智能来自哪里？

```text
Code / Rules
Model
LLM
```

### 12.2 流程是谁决定的？

```text
Developer
Model
Developer + Model
```

### 12.3 模型拥有什么权限？

```text
只生成文本
↓
可以输出结构化决策
↓
可以选择 Tool
↓
可以动态规划下一步
↓
可以产生 Side Effect
```

### 12.4 Runtime 对模型有什么约束？

```text
Permissions
Stop Conditions
Budget
Timeout
Guardrails
Human Approval
```

这些问题比单纯问：

> “这是 Agent 吗？”

更加有工程价值。

## 13. Autonomy Spectrum

这些系统并不是非黑即白。

更适合把它们理解成一个 Autonomy Spectrum：

```text
Low Autonomy
     │
     │ Traditional Application
     │
     │ AI Application
     │
     │ LLM Application
     │
     │ AI Workflow
     │
     │ Tool-Using Agent
     │
     │ Planning Agent
     │
     ▼
High Autonomy
```

随着 Autonomy 提升：

### 优点

- 灵活性增加；
- 能处理更开放的问题；
- 能根据环境动态调整策略；
- 可以执行未知数量的步骤。

### 同时增加的问题

- 不确定性；
- Debug 难度；
- Evaluation 难度；
- Token / Cost；
- Latency；
- Security Risk；
- Tool Risk；
- Production Reliability。

所以：

> **More Autonomy ≠ Better Architecture。**

---

## 14. Engineering Principle

Agent Engineering 中一个非常重要的原则：

> **Prefer the simplest architecture that reliably solves the problem.**

也就是：

```text
能用 Traditional Code 解决
→ 不需要 LLM

能用 Single LLM Call 解决
→ 不需要 Workflow

能用固定 Workflow 解决
→ 不需要 Agent

只有执行路径本身需要运行时动态决策
→ 才考虑 Agent
```

例如支付系统：

```text
扣款
↓
记账
↓
生成流水
```

这种强确定性业务更适合 Workflow / Traditional Code。

而：

```text
分析一个未知项目为什么 CI 失败
```

由于调查路径无法提前完全确定，更适合 Agent。

## 17. Common Misunderstandings

### 17.1 使用 LLM 就是 Agent

错误。

```text
Prompt → LLM → Response
```

只是最基础的 LLM Application。

---

### 17.2 使用 Tool Calling 就是 Agent

错误。

Tool Calling 可以完全存在于固定 Workflow 中。

---

### 17.3 有多个步骤就是 Agent

错误。

```text
A → B → C → D
```

如果路径固定，本质上仍然是 Workflow。

---

### 17.4 Agent 比 Workflow 更高级

错误。

它们解决的问题不同。

Workflow 更：

- 可预测；
- 可测试；
- 易控制；
- 易审计。

Agent 更：

- 灵活；
- 动态；
- 适合开放问题。

---

### 17.5 Agentic System 就是 Multi-Agent

错误。

Agentic System 可以只有一个 Agent，也可以包含多个 Agent，也可以混合固定 Workflow。

## 18. Engineering Decision Checklist

以后设计 AI 系统时，可以依次问：

1. 这个问题可以通过确定性代码稳定解决吗？
2. 是否真正存在需要模型完成的语义任务？
3. Single LLM Call 是否足够？
4. 是否只是需要几个固定 AI 步骤组合？
5. 执行路径是否可以提前完整定义？
6. 是否必须根据运行时 Observation 动态决定下一步？
7. 模型需要哪些 Tools？
8. Tool 是否存在 Side Effect？
9. 哪些行为必须受 Runtime 限制？
10. 是否真的需要 Agent，而不是 Workflow？

## 20. Interview Questions

### Q1：AI Application 和 LLM Application 有什么区别？

关键点：

- AI Application 是更大的概念；
- 可以使用传统 ML、CV、NLP、推荐算法等；
- LLM Application 是以 LLM 为核心智能组件的一类 AI Application。

### Q2：LLM Application 和 Agent 有什么区别？

关键点：

- LLM Application 可以只是一次模型调用；
- Agent 通常需要根据目标和运行时状态持续决策；
- Agent 往往涉及 Tool、Loop、State、Stop Condition 等机制。

### Q3：Workflow 和 Agent 最核心的区别是什么？

关键点：

> Control Flow Ownership。

Workflow 的主要执行路径由代码提前定义；

Agent 的一部分执行路径由模型在运行时动态决定。

### Q4：Tool Calling 就是 Agent 吗？

不是。

固定代码也可以让 LLM 调用 Tool。

需要进一步判断：

> 模型是否能够根据 Observation 持续动态决定下一步行动。

### Q5：为什么不是所有系统都应该使用 Agent？

因为 Autonomy 会带来：

- 不确定性；
- 更高成本；
- 更高延迟；
- 更复杂的 Debug；
- 更复杂的 Evaluation；
- 更大的安全风险。

应该优先使用能够可靠完成任务的最简单架构。

### Q6：什么是 Agentic System？

Agentic System 是围绕目标驱动任务执行构建的完整 AI 软件系统，可以组合：

- Workflow；
- Agent；
- Tools；
- Context；
- State；
- Memory；
- RAG；
- HITL；
- Runtime；
- Evaluation；
- Tracing；
- Security。

---

## 21. One-Sentence Summary

> AI Application 的演进，本质上不是“模型越来越强”这么简单，而是智能能力和运行时决策权逐渐进入软件系统；其中 Workflow 与 Agent 最重要的边界，是 Control Flow 主要由代码预定义，还是由模型根据运行时状态动态参与决策。
